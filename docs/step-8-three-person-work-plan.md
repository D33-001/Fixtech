# Fixtech 1.0 — ขั้น 8: แผนทำงานร่วมกัน 3 คนทีละส่วน

**ฐานงาน:** Fixtech 1.0 สำหรับรายวิชา; ขั้น 1–7 ผ่านการตรวจรับตาม `step-1-7-readiness-review.md` ในสภาพแวดล้อมทดสอบรอบนั้น
**วิธีทำ:** สมาชิกทั้งสามทำเรื่องเดียวกันในแต่ละช่วง ตั้งแต่ทำความเข้าใจ ลงมือ ตรวจ และอธิบาย ไม่แยกคนทำ UI/ฐานข้อมูล/เอกสาร
**เป้าหมายส่ง:** เว็บ Demo เปิดได้, เอกสาร 1–8 ตรงกับระบบ, ผลทดสอบบนเครื่องนำเสนอ, สไลด์และบทสาธิตที่ทุกคนตอบคำถามได้
**เวลา:** ตัวอย่าง 6 สัปดาห์ ปรับตามกำหนดส่งจริงโดยรักษาลำดับและเกณฑ์ผ่าน

## 1. สิ่งที่ทีมกำลังทำ

ระบบมีเว็บภาษาไทย 4 บทบาท: ลูกค้าทั่วไป บริษัท ช่าง/ทีมช่างแบบข้อมูลตัวอย่าง และ Admin. ใช้ Node.js/Express, PostgreSQL schema Demo 26 ตาราง, ภาพหลังยินยอม, AI ผ่าน Ollama/Gemma 3 4B ในเครื่อง, ราคาอ้างอิงที่ทีมคัดสรร, จับคู่/ข้อเสนอ, แชต/แจ้งเตือนในเว็บ, นัดหมาย, ส่งงาน, ประกัน, รีวิว, ข้อพิพาท และ **ชำระเงินจำลอง**. ขั้น 8 ทำให้ทั้งทีมเปิด ตรวจ อธิบาย และส่งมอบระบบที่มีอยู่ได้; ถ้าพบบั๊กให้แก้พร้อมเอกสารและผลทดสอบที่กระทบ.

เงินจริง ราคาตลาดสด การตรวจตัวตนช่างจริง อีเมล/SMS วิดีโอ security audit และการรับรอง WCAG เต็มรูปแบบเป็นแผนขยายภายหลังตาม `production-expansion-v1.md`. ไม่มีบัญชี merchant หรือผู้รับเงินจริง จึงไม่เป็นเงื่อนไขผ่านงานรายวิชา. ใช้ข้อมูลสังเคราะห์เท่านั้น.

## 2. ทำงานพร้อมกันอย่างไร

หนึ่งรอบใช้ประมาณ 60–90 นาที:

1. **10 นาที:** เปิดข้อกำหนด/ผัง/API ของส่วนที่จะทำ ตกลงผลที่ต้องเห็น.
2. **30–45 นาที:** คนหนึ่งจับคีย์บอร์ด อีกคนทวนกฎกับเอกสาร อีกคนลองกรณีผิดพลาดและบันทึกหลักฐาน; ทั้งสามคนดูหน้าจอและตัดสินใจร่วมกัน.
3. **15–20 นาที:** สลับให้คนอื่นลองทำหรืออธิบาย flow โดยไม่ให้คนแรกบอกคำตอบ. ถ้าผิดให้แก้และลองใหม่.
4. **5 นาที:** บันทึกผลจริง ชื่อเครื่อง/ฐานทดสอบ หมายเลข commit และสิ่งค้าง แล้วให้ทั้งสามคนยืนยัน

หมุนหน้าที่ทุกรอบ ไม่ใช่แบ่งเจ้าของงานถาวร:

| รอบ | ลงมือ/แชร์หน้าจอ | ตรวจขั้น 1–7 | ลองผิดพลาด/บันทึก |
|---|---|---|---|
| A | คนที่ 1 | คนที่ 2 | คนที่ 3 |
| B | คนที่ 2 | คนที่ 3 | คนที่ 1 |
| C | คนที่ 3 | คนที่ 1 | คนที่ 2 |

ใช้ A → B → C วนไป. ทั้งสามคนอยู่กับงานเดียวกัน แต่ไม่ยิงคำสั่งแก้ฐานหรือใช้ session เดียวกันพร้อมกัน. ถนัดต่างกันได้ แต่ทุกคนต้องเคยเปิดเว็บ ลอง flow และอธิบายได้.

## 3. ส่วนงานทีละช่วง

### ส่วน 0 — เข้าใจระบบร่วมกัน (1 รอบ)

อ่าน SRS §13, use cases, activity §7, ERD/DDL, API/state, wireframes, สูตรราคา/จับคู่ และผลตรวจรับขั้น 1–7. วาดเส้นทางสั้น ๆ: ลูกค้า → อาการ → consent/AI/ราคา → เผยแพร่ → จับคู่หรือเลือกข้อเสนอ → นัด/ซ่อม → หลังงาน. ให้แต่ละคนอธิบายความต่าง B2C/B2B และข้อจำกัด AI/ราคา.

**ผ่านเมื่อ:** ทั้งสามเล่า flow ตรงกัน; คำที่ยังไม่เข้าใจมีเอกสารอ้างอิงให้กลับไปอ่าน.

### ส่วน 1 — เปิดระบบบนเครื่องที่จะนำเสนอ (1–2 รอบ)

ทำตาม `README.md` และ `operations.md`: Node 22.9+, PostgreSQL ฐาน Demo ว่าง, `.env` ส่วนตัว, DDL 26 ตาราง, seed หนึ่งครั้ง และ Ollama ถ้าจะสาธิต AI ลำดับตรวจคือ `npm run setup:check -- --before-seed` → seed พร้อมตัวแปรอนุญาตชั่วคราว → `npm run setup:check` → `npm run dev` → เปิด `http://localhost:3001` และ `/api/health/ready` ระหว่างพัฒนา nodemon และ BrowserSync จะ restart/reload ให้เอง เมื่อเตรียมนำเสนอให้หยุดด้วย `Ctrl+C` แล้วใช้ `npm start` กับ `http://localhost:3000` เพื่อทดสอบโหมดนิ่ง คนที่เหลือตรวจว่า Terminal อยู่ในโฟลเดอร์โครงการและชี้ฐาน Demo ที่ทิ้งได้จริง ห้ามแชร์รหัสหรือ `.env`

**ผ่านเมื่อ:** เครื่องที่จะสาธิตเปิดเว็บและ ready; ทุกคนรู้วิธีเริ่ม/หยุด. หาก Ollama ไม่พร้อมให้จดไว้และใช้ manual fallback; ไม่อ้างว่าทดสอบ AI จริงบนเครื่องนั้น.

หลังเปิดเว็บ ให้ทั้งสามคนผลัดกันสมัครบัญชีลูกค้าทั่วไปหรือบริษัทด้วยอีเมลตัวอย่างที่ไม่ซ้ำและรหัสที่ตนตั้งเอง ออกจากระบบแล้วเข้าใหม่ ทดสอบรหัสผิด/อีเมลซ้ำ และตรวจว่าไม่มีตัวเลือกสมัครช่างหรือ Admin จากนั้นใช้บัญชี seed ของช่าง/Admin เพื่อเดินงานร่วมกับบัญชีลูกค้าที่สมัครใหม่ ดูขั้นตอนทีละข้อใน `README.md`

### ส่วน 2 — ลูกค้าทั่วไปถึงการจับคู่ (2–3 รอบ)

ใช้บัญชีลูกค้าทั่วไป: กรอกอุปกรณ์/อาการ → consent ก่อนส่งภาพ/AI → วิเคราะห์/สรุป → ดูราคาอ้างอิงพร้อมแหล่งและวันทบทวน → ยืนยันเผยแพร่ → ดูช่างที่จับคู่. สลับกันลองปฏิเสธ consent, AI ไม่พร้อม, ภาพผิดชนิด/ใหญ่เกิน, ราคาใช้ไม่ได้ และไม่มีช่างตรงเงื่อนไข. จด Job ID และภาพหน้าจอที่ไม่มีข้อมูลจริง.

**ผ่านเมื่อ:** ทางปกติและกรณีผิดพลาดสำคัญทำได้; ทุกคนอธิบายว่าราคาเป็น curated reference และ matching กรองคุณสมบัติแล้วเรียง `priority, provider_id`.

### ส่วน 3 — บริษัทและการเลือกข้อเสนอ (1–2 รอบ)

ใช้บัญชีบริษัท: กรอกข้อมูลอุปกรณ์/สถานที่/เวลา/ข้อจำกัด → ดูสรุปและช่วงราคา → ดูข้อเสนอทีมช่างตัวอย่าง 2 ราย → เลือกหนึ่งข้อเสนอ → ไปนัดหมาย. ตรวจว่าเลือกซ้ำไม่ได้และบริษัทอื่นไม่เห็นข้อมูลนี้.

**ผ่านเมื่อ:** มีหลักฐานสถานะก่อนและหลังเลือก; ทั้งสามคนอธิบายได้ว่าช่วงราคายังไม่ใช่ใบเสนอราคาจริงและทีมช่างเป็นข้อมูล Demo.

### ส่วน 4 — ช่างและงานซ่อม (1–2 รอบ)

เปลี่ยนเป็นบัญชีช่าง: เห็นเฉพาะงานตน → แชต/แจ้งเตือน → นัด → เริ่ม → ส่งงานเสร็จ/ระบุประกัน. กลับไปดูฝั่งลูกค้าหลังเปลี่ยนสถานะ. ลองใช้บัญชีช่างอีกคนเปิดงาน/ไฟล์นี้ และลองกดเปลี่ยนสถานะซ้ำหรือก่อนเวลา.

**ผ่านเมื่อ:** สถานะสองฝั่งตรงกัน; สิทธิ์ข้ามบัญชีถูกปฏิเสธ; ทุกคนรู้ว่า API บังคับกฎสถานะ.

### ส่วน 5 — ตรวจรับและหลังงาน (1–2 รอบ)

ลูกค้าตรวจรับ → ชำระ **จำลอง** → รีวิวหนึ่งครั้ง → เปิด warranty ticket หรือ dispute → Admin บันทึกผล. ใช้ Job ทดสอบแยกถ้าจำเป็น. ตรวจ B2B ชำระผ่านระบบจำลองเท่านั้น; B2C เลือกจ่ายตรงหรือผ่านระบบจำลองและช่างยืนยันรับตาม flow. ลองกดซ้ำและผิดสิทธิ์.

**ผ่านเมื่อ:** มีผลจริงและภาพของ flow หลังงาน; ทุกคนอธิบายได้ว่าไม่มีการรับ/คืนเงินจริงหรือ escrow.

### ส่วน 6 — ไล่ความตรงกันของขั้น 1–7 (1–2 รอบ)

เลือก Job จากส่วน 2–5 แล้วไล่: SRS → use case → activity → ตาราง/keys ใน ERD → API/state → UI → ราคา/ลำดับช่าง. ตรวจ schema 26 ตาราง, ราคาและหน่วยเงิน, ความสดของแหล่ง curated, `409` เมื่อ Draft เปลี่ยนระหว่างรอ AI/ราคา และตัวอย่างคำนวณราคาด้วยมือ. ถ้าไม่ตรง ให้จดขั้นตอนทำซ้ำ แก้ต้นเหตุ และแก้เอกสารที่ได้รับผล.

**ผ่านเมื่อ:** ชี้หลักฐานเชื่อมครบ 1–7 ได้สำหรับอย่างน้อยหนึ่ง Job; จุดขัดแย้งที่พบถูกแก้หรือระบุเป็นข้อจำกัดตามจริง.

### ส่วน 7 — ทดสอบซ้ำและตรวจหน้าจอ (1–2 รอบ)

รัน `npm run check`, schema test และ `npm test` บนฐานทดสอบแยกที่ทิ้งได้ตาม `operations.md`; บันทึกจำนวนผ่าน/skip โดยเฉพาะ PostgreSQL integration. อย่าใช้ฐานมีค่าหรือฐานที่เพื่อนกำลังสาธิต. เปิดเว็บ 4 บทบาทที่ 320/768/1280 CSS px; ลอง keyboard focus, loading/empty/error และ logout/login ข้ามบัญชี.

**ผ่านเมื่อ:** มีคำสั่ง ชื่อเครื่อง ฐาน หมายเลข commit และผล test ของรอบปัจจุบัน flow หลักไม่มีบั๊กที่หยุดสาธิต และไม่มี action สำคัญซ่อนหรือล้นจอ ผลจากรายงานเดิมใช้แทนผลบนเครื่องนำเสนอไม่ได้

### ส่วน 8 — เอกสารและนำเสนอ (1–2 รอบ)

ร่วมกันปรับคู่มือเปิด, ข้อจำกัด, ผัง, ERD, หน้าจอ, API/state, สูตรและหลักฐานทดสอบให้เป็นรุ่นเดียวกัน. สไลด์เรียง: ปัญหา → ผู้ใช้/ขอบเขต → flow → ข้อมูล/API → ราคา/จับคู่ → สาธิต → ผลทดสอบ/ข้อจำกัด. ซ้อมจับเวลาและหมุนคนนำ. เตรียมภาพสำรอง AI หากเครื่องช้า พร้อมบอกว่าเป็นภาพจากการทดสอบ.

**ผ่านเมื่อ:** ทั้งสามคนเปิดตามคู่มือและตอบเรื่อง 4 บทบาท/26 ตาราง/API/สูตร/ข้อจำกัดได้; สาธิตจบในเวลาที่กำหนด.

**ส่วนเสริมจากสไลด์รายวิชา (ทำร่วมกันในรอบเดียว ไม่แบ่งคนละงาน):** เตรียมแผนภาพสถาปัตยกรรมและเหตุผลเลือก Express/`pg`/PostgreSQL/เว็บสำหรับ CE385; ถ้ารายวิชากำหนด Swagger/OpenAPI ให้สร้างจาก route ที่ทำงานจริงและตรวจด้วย HTTP จริง. สำหรับ CE396 ให้เตรียม ERD ไฟล์ภาพและต้นฉบับ, DDL, seed, ตัวอย่าง FD → 1NF/2NF/3NF พร้อมเหตุผลของ snapshot, และคำสืบค้นตอบคำถามธุรกิจอย่างน้อย 5 ข้อที่รันจริง. เอกสาร [ผลเทียบสไลด์](course-slide-alignment-review.md) แยกสิ่งที่มีแล้วกับสิ่งที่ยังเป็นงานเตรียมนำเสนอ. ก่อนส่ง GitHub/สไลด์ให้ทั้งสามคนตรวจประวัติการมีส่วนร่วมและตอบส่วนที่ตนลงมือได้; การทำพร้อมกันไม่ยกเว้นหลักฐานการมีส่วนร่วม.

## 4. ปฏิทินตัวอย่าง

| สัปดาห์ | ทั้งทีมทำส่วน | หลักฐานเมื่อจบ |
|---|---|---|
| 1 | 0–1 | เข้าใจ flow; เครื่องนำเสนอเปิดเว็บ/ฐานได้ |
| 2 | 2 | B2C และกรณีผิดพลาดสำคัญ |
| 3 | 3–4 | บริษัทเลือกข้อเสนอ; ช่างเดินงาน; สิทธิ์ถูกต้อง |
| 4 | 5–6 | หลังงาน/Admin; trace ขั้น 1–7 |

ถ้าเวลาสั้นลง ลดจำนวนรอบ แต่ยังให้ทั้งสามคนตรวจ flow สำคัญร่วมกัน. แก้บั๊กที่ทำให้สาธิตล้มก่อนงานตกแต่งเพิ่มเติม.

## 5. ตารางบันทึกงานเดียวของทีม

| ส่วน/เคส | สถานะ | เครื่อง/ฐาน/commit | ผู้ลงมือ · ผู้ตรวจ · ผู้บันทึก | ผลคาด → ผลจริง | หลักฐาน/บั๊ก | รอบถัดไป |
|---|---|---|---|---|---|---|
| ตัวอย่าง: 2/ปฏิเสธ consent | รอตรวจ | ลงเมื่อทดลอง | A/B/C | ไม่ส่งภาพ/ไม่เรียก AI → ... | ภาพ/error | ให้คนอื่นลองซ้ำ |

สถานะใช้ `ยังไม่เริ่ม`, `กำลังทำ`, `รอตรวจ`, `ผ่าน`, `ติดปัญหา`. บั๊กเขียน “บัญชี/ข้อมูลเริ่มต้น → ทำอะไร → คาดอะไร → เกิดอะไร → หลักฐาน”. ไม่เก็บรหัส, `.env`, ภาพส่วนตัว หรือข้อมูลลูกค้าจริง. เมื่อแก้ code/schema/API/state/ราคา ให้ปรับเอกสารและทดสอบเคสเดิมซ้ำ. การเปลี่ยน DDL 26 ตารางต้องตกลงทั้งทีม เพราะกระทบขั้น 4–7.
