# สถานะการตรวจรับ — Fixtech Demo v1.8

เอกสารนี้เก็บหลักฐานการตรวจตามลำดับเวลา ข้อความ “ยังไม่ผ่าน” ในหัวข้อเก่าเป็นสถานะ ณ เวลานั้น ไม่ใช่ข้อสรุปล่าสุด ให้ใช้หัวข้อ **ผลตรวจรับขั้น 1–7 รอบสุดท้าย** และ **ข้อสรุปการตรวจรับ** เป็นสถานะปัจจุบัน

## 1. พื้นฐานสำหรับขยายสู่ production — 26 กันยายน 2026

- ติดตั้ง DDL ของ Demo v1.8 และ `release/migrations/0001_production_foundations.sql` บน PostgreSQL 18.6 ชุดใหม่ที่ทิ้งได้สำเร็จ จำนวนตารางหลักใน `public` เพิ่มจาก 26 เป็น 34 ตาราง มีบันทึก migration และมี partial unique index สำหรับ rate card ที่ใช้งานหนึ่งรายการต่อ provider/segment กับ payment intent ที่ยังเปิดอยู่หนึ่งรายการต่องาน
- ชุดทดสอบนโยบาย production ผ่าน 3/3 กรณี การรับ webhook ผ่าน 1/1 หลังแก้ชนิด parameter ของ PostgreSQL และการจำลองผลจากผู้ตรวจตัวตน/การอนุมัติของ Admin กับความครอบคลุมของราคาเครือข่ายปัจจุบันผ่าน 1/1 ทั้งหมดใช้ response สังเคราะห์ที่ฉีดเข้าระบบ ไม่ใช่ผู้ให้บริการที่ทำสัญญาจริง
- adapter ของ Opn ใน test mode ผ่าน 2/2 กรณีด้วย HTTP double โดยตรวจ origin ของ API, การบังคับ test key, parameter ฝั่ง server และการอ่าน charge กลับ แต่ยังไม่ได้เชื่อมบัญชีร้านค้าจริง
- เคยสั่ง `npm audit --omit=dev --audit-level=high` แต่ npm ติดต่อ advisory endpoint ไม่ได้ จึงยังยืนยันสถานะช่องโหว่ dependency ไม่ได้ และห้ามนับว่า security audit ผ่าน
- การหัก/คืนเงินจริง การรับช่างจริง สิทธิ์และความครอบคลุมของข้อมูลราคา UI production, settlement ledger, reconciliation, audit และการตรวจ accessibility เต็มรูปแบบยังไม่ได้พัฒนา ตัวป้องกันการเปิด Demo ด้วย production mode ยังทำงานอยู่ ดูรายละเอียดที่ [การประเมินความพร้อม production](production-readiness-review.md)

## 2. การตรวจ UI สี่บทบาทรอบทบทวน — 25 กันยายน 2026

ณ รอบนี้ production ยัง **ไม่ผ่านการตรวจรับ** เพราะยังไม่มีสัญญา/บัญชี payment provider, แหล่งราคาปัจจุบันที่มีสิทธิ์ใช้, การยืนยันตัวตนช่างจริง และ release gate สำหรับ production ระบบจึงตั้งใจหยุดตอนเริ่มเมื่อใช้ `NODE_ENV=production`

- ทดสอบผ่านเบราว์เซอร์กับ PostgreSQL 18.6 ที่แยกและทิ้งได้ พร้อมบัญชีสังเคราะห์ 8 บัญชี ลูกค้าทั่วไปปฏิเสธ AI แล้วใช้สรุปแบบ manual/ราคา curated ก่อนเผยแพร่เพื่อจับคู่อัตโนมัติ ลูกค้าบริษัทยอมรับช่วงราคา เลือกหนึ่งในสองข้อเสนอ ช่างเห็นงานที่ได้รับมอบหมาย และ Admin เห็นงานกับคิวรับประกัน/ข้อพิพาท โดย browser error log ว่าง
- การตรวจนี้เป็น smoke test ของบทบาทและเส้นทางหลัก ไม่ใช่การทดสอบทุก dialog, ทุกอุปกรณ์ หรือบริการ payment/KYC/ราคาจริง
- พบว่าการ์ดงานของบัญชีก่อนหน้าค้างชั่วคราวระหว่างเปลี่ยนบัญชี จึงล้างรายการงานและรายการ Admin ตอน logout และก่อนวาด dashboard ใหม่ แล้วทดสอบซ้ำสำเร็จ
- หลังแก้ `npm run check` ผ่าน และ `npm test` กับฐาน integration แยกผ่าน 30/30 โดยไม่ข้ามกรณีทดสอบ
- `.env` ถาวรของเครื่องในเวลานั้นยังใช้ credential และ secret ตัวอย่าง การทดสอบใช้ environment ชั่วคราวและไม่แก้ฐานเดิมของผู้ใช้

## 3. การทบทวนความสอดคล้องข้ามขั้น — 25 กันยายน 2026

- ตรวจขั้น 1–7 ร่วมกันและแก้ให้ตรงกันเรื่องความยินยอมก่อนอัปโหลดภาพ จุดเริ่มรับประกันเมื่อยอมรับว่างานเสร็จโดยไม่ผูกกับ payment simulation, ราคา curated ที่ไม่ใช่ข้อมูลสด, session แบบ signed cookie และสัญญาระหว่าง UI/API ดูรายละเอียดใน [ผลทบทวนขั้น 1–7](step-1-7-optimization-review.md)
- หลังแก้ `npm run check` ผ่าน, การตรวจ schema แบบ static ผ่าน 8/8 และ `npm test` บน PostgreSQL 18.6 ใหม่พร้อม seed ผ่าน 30/30 โดยไม่ข้าม
- เพิ่ม regression test สำหรับการแก้ Draft โดยข้อมูลไม่เปลี่ยน และการทิ้งผล AI/price provider ที่ตอบช้าเมื่อ Draft ถูกแก้ระหว่างรอ
- รอบนี้ไม่ได้ทำ browser walkthrough และ performance benchmark ใหม่ทั้งชุด จึงอ้างหลักฐาน UI จากรอบตรวจสี่บทบาท ส่วน automated test ยืนยันโค้ด/schema/workflow แต่ไม่ยืนยันความพร้อม production หรือความเร็ว

## 4. หลักฐานฐานข้อมูลและ workflow — 24 กันยายน 2026

- `npm run db:verify` ติดตั้ง DDL บน PostgreSQL 18.6 ที่ทิ้งได้สำเร็จ พบ 26 ตาราง, 215 คอลัมน์, 57 foreign key, 26 primary key, 13 unique constraint, 54 check constraint และ 53 index การทดสอบ rollback ผ่าน และลบ cluster ชั่วคราวแล้ว
- workflow แอปถึง PostgreSQL ผ่าน โดยใช้ HTTP route, cookie session และฐานจริง ครอบคลุมลูกค้าทั่วไปอัปโหลดภาพหลังยินยอม วิเคราะห์ AI ประเมินราคา จับคู่และคุ้มครองข้อมูลช่าง; ลูกค้าบริษัทเลือกข้อเสนอ; นัดหมาย แชต เริ่มงาน ส่งงาน ยอมรับงาน; เสนอ/เคลมประกัน; payment simulation ทั้งแบบตรงและผ่านแพลตฟอร์ม; รีวิว; ส่งหลักฐานข้อพิพาท และการตัดสิน/บันทึก audit ของ Admin
- การทดสอบพบชื่อฟิลด์เจ้าของงานฝั่งช่างไม่ตรงกัน และ parameter PostgreSQL ในการตัดสินข้อพิพาทมีชนิดกำกวม แก้แล้วจึงผ่าน
- ชุดทดสอบ API/state ของขั้น 5 ใน revision นั้นผ่าน 12/12 ครอบคลุม Q&A กับ AI 20 รอบและปฏิเสธรอบ 21, การคง provenance ราคา, นัดหมายชนกัน, ห้ามเริ่มก่อนเวลา, ความเป็นส่วนตัวของแชต, ข้อความรับประกันแบบมีโครงสร้าง, ป้องกัน idempotency key ข้ามงาน และห้ามเปิดงานที่จบแล้วซ้ำจากการตัดสินข้อพิพาท
- browser walkthrough ก่อนหน้าเคยพบ CSS ทับ `hidden`, company-only field โผล่ให้ลูกค้าทั่วไป, การใช้งาน `event.currentTarget` หลัง async และไม่มี refresh/error boundary หลังสร้าง Draft ทั้งหมดได้รับการแก้และ smoke test ซ้ำ
- การปรับ UI ขั้น 6 เปลี่ยน prompt/confirm/alert ของ browser เป็น dialog ในแอปสำหรับ AI, ราคา, ข้อเสนอ, นัดหมาย, แชต, ส่งงาน, payment simulation, รีวิว, รับประกัน, ข้อพิพาท, แจ้งเตือน และคำตัดสิน Admin รวมทั้งย้ายคำขอความยินยอมมาไว้ก่อนอัปโหลดภาพ
- ณ เวลานั้นการตรวจ static ที่ desktop/mobile ไม่พบแนวนอนล้น แต่ยังรอ authenticated walkthrough ใหม่ครบสี่บทบาท สถานะค้างนี้ถูกปิดแล้วในหัวข้อผลตรวจรับรอบสุดท้ายด้านล่าง

## 5. การตรวจขั้น 7 และ AI จริงในเครื่อง — 25 กันยายน 2026

- ติดตั้ง schema และ seed v3 บน PostgreSQL 18.6 ชั่วคราว ตรวจว่า pricing rule v1/v2 ไม่ active และ v3 active พร้อม `platformMarkupRate=0.15` จากนั้น `npm test` ผ่าน 29/29 โดยไม่ข้าม การทดสอบครอบคลุมราคา curated หมดอายุทั้งตอนสร้าง/ยอมรับ/เผยแพร่, การคงงานเป็น `READY_TO_PUBLISH`, การปฏิเสธ multiplier จาก client, workflow B2C/B2B และการเลือก provider ที่ให้ผลซ้ำได้
- ทดสอบผ่าน browser ว่าราคา B2C แสดงวันที่ทบทวน วันหมดอายุ 30 วัน คำเตือนว่าไม่ใช่ราคาสด/ราคาเฉพาะเคส และ URL แหล่งข้อมูล เมื่อใช้ `NODE_ENV=test` กับ `FIXTECH_TEST_CURATED_REVIEWED_AT=2026-08-01T00:00:00.000Z` ระบบแสดงว่าข้อมูลหมดอายุและไม่สร้างราคา โดยไม่เปลี่ยนวันที่จริงใน catalog
- adapter Ollama รับข้อความและภาพที่เลือก ตรวจ structured JSON, จำกัดเวลา และปกปิดข้อความส่วนบุคคลแบบ best effort หาก integration ผิดพลาดจะคืน 502/503 ที่ปลอดภัยแทน 500 ทั่วไป
- เพิ่ม safety fallback แบบกำหนดผลซ้ำได้สำหรับคำแนะนำที่ตรงกับรูปแบบเสี่ยง เช่น เปิด/ทำความสะอาดฮาร์ดแวร์หรือคำสั่งซอฟต์แวร์ทำลายข้อมูล อย่างไรก็ตามกฎนี้ครอบคลุมเฉพาะรูปแบบที่รู้จัก ไม่ใช่ระบบรับรองความปลอดภัย AI
- seed ต้องมี `DEMO_SEED_ALLOW_MUTATION=yes`; integration test ต้องมี `FIXTECH_TEST_DATABASE_ALLOW_MUTATION=yes` ทั้งคู่ปิดเป็นค่าเริ่มต้นและ seed ถูกปฏิเสธใน production
- smoke test ข้อความจริงผ่าน `createOllamaProvider` กับ `gemma3:4b` ได้ฟิลด์ครบและถามต่อได้ Ollama รายงานโมเดล Gemma 3 4.3B Q4_K_M ขนาด 3,338,801,804 ไบต์
- smoke test ภาพจริงผ่านในระดับการส่งข้อมูลและ schema โมเดลเข้าใจหัวข้อเอกสาร แต่ตอบรายละเอียดอย่างน้อยหนึ่งจุดไม่ถูกและให้คำแนะนำกว้าง จึงต้องถือผลภาพเป็น Draft ที่มนุษย์ตรวจ ไม่ใช่ข้อเท็จจริง
- ช่วง 300–2,500 บาทสำหรับซอฟต์แวร์ระยะไกล และ 500–800 บาทสำหรับตัวอย่างฮาร์ดแวร์เป็นข้อมูลกว้างจากหลายผู้ให้บริการ ขอบเขต ระดับบริการ ค่าเดินทาง และอะไหล่อาจต่างกัน ต้องแสดงคำเตือนและลิงก์เสมอ

## 6. ผลตรวจรับขั้น 1–7 รอบสุดท้าย — 25 กันยายน 2026

- **ฐานทดสอบ:** ผ่าน ใช้ PostgreSQL 18.6 ใหม่บน loopback แยกฐาน UI และ integration ติดตั้ง release schema และ `npm run setup:check` พบ 26/26 ตารางกับ 8/8 บัญชีสังเคราะห์ โดยไม่แก้ `.env` หรือฐานถาวรของผู้ใช้
- **การตรวจอัตโนมัติ:** `npm run check` ผ่าน, `npm test` ผ่าน 30/30 โดยไม่ข้าม และ `python -m unittest tests/check_demo_v18_schema.py` ผ่าน 8/8 รวมกรณีไฟล์ภาพ/MIME ไม่ถูกต้อง ขนาดเกิน 10 MiB เกินสามไฟล์ และผู้ใช้อีกบริษัทพยายามอ่านไฟล์ private
- **browser acceptance:** ผ่านครบ B2C, B2B, ช่าง และ Admin ลูกค้าทั่วไปเดินตั้งแต่ consent → อัปโหลด private → Ollama/Gemma → ราคา curated → เผยแพร่/จับคู่ → แชต/นัดหมาย → ส่งและยอมรับงาน/รับประกัน → payment simulation/รีวิว/เคลม/ข้อพิพาท ช่างจัดการงานที่ได้รับ ส่วน Admin ตัดสินเคลมและข้อพิพาท ลูกค้าบริษัทสร้างงาน รับสองข้อเสนอ เลือกหนึ่งข้อเสนอ และเข้าสู่สถานะรอนัดหมาย
- **fallback และ regression UI:** เมื่อปฏิเสธ AI ระบบไม่เรียก AI และไม่อัปโหลดภาพ พร้อมให้ใช้ manual summary การตรวจพบ service format เก่าค้างหลัง reset form จึงแก้และทดสอบเส้นทางบริษัทแบบ Hardware/Onsite ซ้ำ
- **responsive และ keyboard ขั้นพื้นฐาน:** ที่ความกว้าง 320, 768 และ 1280 CSS px ไม่พบแนวนอนล้น การกด Tab เห็น focus outline, browser console ไม่มี error และคู่สีข้อความที่แก้ในรอบนี้มี contrast ที่คำนวณได้อย่างน้อย 4.5:1 ทั้งนี้ไม่ใช่การรับรอง WCAG เต็มรูปแบบ
- ข้อมูลที่เกิดขึ้นในฐานทดสอบเป็นข้อมูลสังเคราะห์ทั้งหมด และ cluster ชั่วคราวถูกปิดหลังตรวจ

ผลนี้ใช้แทนข้อความค้างจากรอบขั้น 6 และผล 29/29 ก่อนหน้า แต่ไม่ได้ยืนยันว่า `.env` ถาวรในเครื่องผู้ใช้ถูกตั้งค่าถูกต้อง และไม่ได้อ้างว่า production, payment จริง, ราคาตลาด real-time, AI accuracy/safety เต็มรูปแบบ, WCAG certification หรือ security audit ผ่านแล้ว

## 7. ข้อจำกัดที่ยังคงอยู่

- AI จริงผ่าน smoke test ด้านการเชื่อมต่อและรูปแบบข้อมูล แต่ยังไม่มีการประเมินคุณภาพกับชุดข้อมูลใหญ่และไม่มีการรับรองคำตอบ กฎ safety ครอบคลุมเฉพาะ pattern ที่กำหนด
- ราคา curated ไม่ใช่ real-time และครอบคลุมเพียง workflow ตัวอย่างสองกลุ่ม
- payment เป็น simulation ไม่มี gateway, settlement หรือ refund จริง
- อีเมล/SMS, วิดีโอ, การสมัครและยืนยันตัวตนช่างจริง, production deployment และ security review ยังไม่เสร็จ
- `npm audit` เคยติดต่อ advisory endpoint ไม่ได้ จึงยังไม่ทราบสถานะช่องโหว่ dependency ล่าสุด
- เมื่อไม่มี `FIXTECH_TEST_DATABASE_URL`, `npm test` จะข้าม integration test ของ PostgreSQL ต้องทำตาม [คู่มือเดินระบบ](operations.md) เพื่อทดสอบเต็มชุด
- seed มีเพียงสามเขตในกรุงเทพฯ และช่างสังเคราะห์สี่บัญชี ไม่ได้พิสูจน์ว่ามีช่างจริงครอบคลุมทุกเขต

## 8. ข้อสรุปการตรวจรับ
